# Writing agent instructions and workflows

Apply when creating or changing rules, skills, subagents, or agent-tool workflows.

  * Before adding an instruction, identify the concrete mistake it prevents or the necessary context it supplies. After an agent failure, check whether existing guidance was unclear, conflicting, not loaded, or not followed. Address the identified cause and keep one authoritative source; clarify existing guidance when needed instead of adding a duplicate.
  * Keep always-loaded rules for durable constraints, expected outcomes, and necessary context the agent cannot reliably infer. In these rules, leave preferences and workflow choices to the task or project unless a method is required by an explicit constraint or needed for correctness or safety. Put task-specific procedures, scripts, and detailed examples in skills or references loaded when needed. A specialised topic alone does not make an instruction a skill. Use the narrowest applicable scope. Keep temporary task state out of permanent policy.
  * Write plain, direct instructions with consistent terms, concrete actions, and expected results. Make clear who should act when that could be misunderstood. If "it," "this," or "they" could refer to different things, name the intended item. Add a short example only when needed to prevent ambiguity.
  * Write standing rules so the agent can recognise their conditions from context without a reminder or invocation. Put conditions before the actions they qualify and keep exceptions nearby, so loading a rule does not itself start unrelated work. Where a prohibition leaves the next action unclear, state a safe alternative without weakening the restriction. Preserve technical precision and safety limits.
  * For each reference, give a verified path or authoritative URL and state when to read it. Keep essential safety and approval boundaries in the applicable entry point, not solely optional links. Do not require unrelated references together.
  * Keep skill and subagent descriptions short: purpose and when to use them. Put required inputs, outputs, and procedures in the body. When writing a skill, subagent, or workflow, state how to tell when the work is complete. Check the target agent's format and loading behaviour; do not assume inherited context or capabilities. Choose whether a skill or workflow may start automatically or needs an explicit user request. Set supported activation controls to match.
  * For workflows that repeat or delegate work, define stop conditions and bounded retries. For tasks intended to finish, set task-appropriate limits on total iterations or agent runs, not just how many run at once. For authorised ongoing workflows, define cancellation or expiry conditions and bound work per run instead of imposing an arbitrary total-run cap. Enforce limits with available workflow controls; report unfinished work when a limit is reached.
  * When splitting, shortening, or combining instructions, preserve their scope, conditions, and exceptions. Check the resulting files independently and in intended combinations for missing context, duplication, or conflicts. Review wording-only changes for clarity, consistency, and unchanged meaning.
  * For changes to activation, permissions, or workflows, verify representative affected cases. Where relevant, also check cases where the rule or workflow should not apply. Before claiming improved agent behaviour, compare the previous and revised instructions on representative tasks under comparable conditions. During rule maintenance, re-evaluate model- or tool-specific workarounds after relevant changes. Retire or narrow them when representative comparisons show they no longer help; preserve still-needed safety boundaries. Limit claims to what was tested.
