# Web accessibility rules

Apply accessibility requirements to the requested work. Do not start a broader accessibility audit unless the task or project requirements call for it.

  * Follow the project's accessibility requirements and supported environments. Ask about missing requirements only when they could materially change the work; do not invent a conformance target.
  * For changes affecting accessibility, preserve supported interactions in the affected flow, including dynamic updates and recovery states. Select checks by the changed behaviour and project requirements, not a fixed list of devices or test methods. Available tools alone are not a reason to expand testing.
  * Treat automated checks, linters, and browser inspection as evidence only for the cases they cover. Do not claim full conformance from a partial review.
  * For shared components and third-party embeds, identify affected consumers and separate what the project controls from what it does not. Do not use a visual-only workaround to hide an inaccessible integration.
  * For accessibility assessments, establish the agreed standard, level, coverage, and exclusions; report methods, remaining barriers, and limits. Keep unrequested audit artifacts and monitoring tools out of the project.
